# LLM-Lesung

**LLM-based analysis of Germany's parliament's bill drafts** — an adaptation of
Estonia's amazing *LawLab / "Apsakaleidja"* ([lawlab.ilves.ai](https://lawlab.ilves.ai)), the tool
to find errors in laws with an LLM. Background on the original: [WIRED](https://www.wired.com/story/the-28-million-dollar-mistake-that-inspired-estonias-ai-fuckup-finder/).

LLM-Lesung pulls current Gesetzentwürfe from the Bundestag, analyzes each with Claude for
concrete drafting defects, assigns a risk level, and presents the results on a website.

> **Disclaimer:** The findings are generated by a language model. They are unreviewed and may
> be wrong or incomplete. LLM-Lesung is an independent experiment in machine reading: not an
> authority, and not legal advice or a political recommendation. It is of course also not an official
> Bundestag offering.

## Architecture

```
DIP API + Drucksachen-PDFs  →  pipeline (Claude)  →  SQLite  →  FastAPI  →  React SPA
```

- **Pipeline** (`backend/pipeline.py`) — a batch CLI: fetch bill metadata from the Bundestag
  DIP API, download the Drucksache PDF, extract text with `pypdf`, analyze with Claude
  (one structured call per bill), derive the bill risk, and store findings in SQLite.
- **Adversarial pass** (`backend/redteam_pipeline.py`) — a second batch CLI over the stored
  bills: asks what a bad-faith actor gets out of each draft as written and stores the
  exploits beside the findings. It never changes a bill's findings or risk.
- **SQLite** (`data/llm-lesung.db`) — the single shared state; no ORM, no external DB.
- **FastAPI** (`backend/server.py`) — read-only JSON API (`/api/bills`, `/api/bills/{id}`,
  `/api/meta`) that, in production, also serves the built SPA from `frontend/dist`.
- **Reader feedback** — each finding and exploit on the detail page has a small form
  (correct / not correct, optional text). `POST /api/feedback` appends it to
  `data/feedback/<YYYY-MM>.jsonl` (`FEEDBACK_DIR`) together with a snapshot of the rated
  finding; nothing about the sender is stored, and the database is never written.
- **React SPA** (`frontend/`) — Vite + TypeScript, list page with risk-filter cards, per-bill
  detail page, about page, DE/EN UI toggle.

Web serving and data production are fully decoupled — they share only the SQLite file.

## Setup

Requires Python 3.13 + [uv](https://docs.astral.sh/uv/) and Node 22 + npm.

The most common operations are wrapped in a `Makefile`: `make setup`, `make test`,
`make pipeline LIMIT=20`, `make pipeline-all`, `make locate-quotes` (page links for the
findings already stored, no Claude call), `make redteam LIMIT=20`, `make serve` (build + run on :8000),
`make dev` (hot reload). The sections below show the underlying commands.

```bash
# Backend dependencies
uv sync

# Frontend dependencies
cd frontend && npm install && cd ..

# Configuration — copy the template and fill in as needed
cp .env.example .env
```

### Environment variables

All are read from `.env` (or the process environment). The web server needs **none** of
these. The analysis pipeline authenticates like Claude Code (it runs on the Claude Agent
SDK): a local `claude login` (claude.ai subscription) works with no configuration at all.

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `ANTHROPIC_API_KEY` | No | — | Set only to bill the pipeline against the Anthropic API instead of the local Claude Code login. |
| `CLAUDE_CODE_OAUTH_TOKEN` | No | — | Subscription token from `claude setup-token`, for headless/container runs without a local login. |
| `DIP_API_KEY` | No | built-in public key | Bundestag DIP API key. A working public key ships as the default. It rotates ~yearly; if it stops working, re-scrape it from [`dip.bundestag.de/dip-config.js`](https://dip.bundestag.de/dip-config.js), or request a personal key from `parlamentsdokumentation@bundestag.de`. |
| `ANALYSIS_MODEL` | No | `claude-sonnet-5` | Claude model for analysis (override for cheaper/experimental runs). |
| `ANALYSIS_EFFORT` | No | `high` | Reasoning effort of the analysis call (`low`, `medium`, `high`, `xhigh`, `max`). |
| `REDTEAM_MODEL` / `REDTEAM_EFFORT` | No | `ANALYSIS_MODEL` / `ANALYSIS_EFFORT` | Model and reasoning effort of the adversarial pass (Angreifer). |
| `LLM_LESUNG_DB` | No | `./data/llm-lesung.db` | Path to the SQLite database file. |
| `CONTACT_EMAIL` | No | — | Contact address shown on the About page; unset hides the contact section. |

`.env.example` lists the remaining tuning variables.

## Running the analysis pipeline

Populates / refreshes the database. Start small — every analyzed bill costs a Claude call.

```bash
uv run python -m backend.pipeline --limit 5
```

Flags:

- `--limit N` — only fetch the first N bills from DIP (default: all, ~340).
- `--force` — re-analyze every bill even if it appears unchanged.
- `--skip-analysis` — stop after metadata + status refresh (no PDF download, no Claude call).

Each analysis reads the Gesetzentwurf together with its Beschlussempfehlungen (the committee
recommendations), so findings describe the draft as amended in committee. Inputs are never
truncated: a bill whose documents sum to more than 1M characters is skipped and logged.

Re-runs are idempotent: a bill is analyzed again only when its documents or the prompt version
changed, and a failed analysis is retried on the next run. Daily is plenty — the Bundestag does
not move faster.

### Adversarial pass

A second, separate job red-teams the bills already in the database — it needs no DIP access
and reads only the Gesetzentwurf:

```bash
uv run python -m backend.redteam_pipeline --limit 5
```

- `--limit N` — red-team at most N bills whose pass is missing or outdated (default: all).
- `--force` — red-team every bill even if its stored pass is current.

A bill is red-teamed again only when its Gesetzentwurf changed or the adversarial prompt
version did. The exploits are stored separately from the findings and never enter a bill's
risk.

## Evaluation

The project aims to build a set of evaluation cases that score the analysis for precision
(are the findings real?) and recall (are known defects found?). The cases start out
LLM-generated from two sources:

- **Online sources**: press coverage, Constitutional Court rulings and expert criticism of
  bills.
- **Draft evolution**: defects that the committee fixed between the Gesetzentwurf and its
  Beschlussempfehlung.

Reader feedback on individual findings is meant to feed in later. The test set, the harness
and the `make eval-*` targets are described in [`eval/README.md`](eval/README.md).

## Docker

A multi-stage `Dockerfile` builds the frontend (node:22) and packages it with the backend
(python:3.13) into one image that serves `/api/*` and the SPA on port 8000.

`compose.yaml` is the local file (builds from source, port 8000, reads `.env`);
`compose.prod.yaml` is the one `make deploy` copies to the instance (pre-built image,
port 80, plus an optional Cloudflare Tunnel).

```bash
# Build + run (mounts ./data for the SQLite file, reads .env for secrets)
docker compose up --build

# Run the pipeline as a one-off against the same volume
docker compose run --rm web python -m backend.pipeline --limit 10

# Refresh a running deployment (e.g. from host cron, daily)
docker compose exec web python -m backend.pipeline
```

Or without compose:

```bash
docker build -t llm-lesung .
docker run --rm -p 8000:8000 -v "$PWD/data:/app/data" --env-file .env llm-lesung
```

## Deployment (AWS, single EC2)

A prototype deployment to one small EC2 instance, defined as Terraform in [`infra/`](infra/).
All analysis stays local — you run the pipeline on your machine and **upload the finished
SQLite DB**; AWS only serves the read-only site. The instance has **no public access**:
inbound HTTP and SSH are restricted to your own IP, so only you can reach it.

**Prerequisites**

- [Terraform](https://developer.hashicorp.com/terraform/install) ≥ 1.6, Docker with `buildx`.
- AWS CLI v2 with credentials configured (`aws configure --profile <name>`, or SSO), and an
  SSH keypair (`ssh-keygen -t ed25519`) — both live outside this repo.

**Credentials** — `.env` carries a profile name and a key path, not the secrets themselves;
both are required and have no defaults, so a deployment that names neither fails instead of
guessing an account:

```bash
AWS_PROFILE=        # a profile in ~/.aws/credentials — not a key
SSH_KEY=            # path to the private key; <SSH_KEY>.pub must sit beside it
```

The region comes from that profile (`region` in `~/.aws/config`).

**First-time setup**

```bash
cp .env.example .env                           # set AWS_PROFILE and SSH_KEY
aws sts get-caller-identity --profile <name>   # confirm it's the right account
cd infra
cp terraform.tfvars.example terraform.tfvars   # then `make infra-ip` fills my_ip (+ my_ipv6 /64)
cd ..
make infra-up      # terraform apply — creates the instance (billable)
make deploy        # build the image locally, ship it, start the container
make push-db       # upload data/llm-lesung.db
```

**View the site** — it's reachable only from your `my_ip` / `my_ipv6` prefix, so just browse to the URL that
Terraform prints:

```bash
cd infra && terraform output -raw url && cd ..   # e.g. http://18.184.x.x; url_ipv6 for IPv6
```

**Redeploying**

```bash
make deploy        # after a code change
make push-db       # after a new local pipeline run
make push-eval     # upload the HTML reports in data/eval-public/
make pull-feedback # download the reader feedback into data/feedback/
make infra-ip      # after your ISP gives you a new IP, then: make infra-up
make ssh-ec2       # shell on the box;  make dockerlogs  follows container logs
make infra-down    # tear everything down
```

Notes: the instance gets a **fixed public IP** (Elastic IP), so the URL survives stop/start
and stays bookmarkable. When *your ISP* address or IPv6 prefix changes, run `make infra-ip`
and re-run `make infra-up`, or you'll lock yourself out. An Elastic IP is billed whether or
not the instance runs, so tear down with `make infra-down` rather than stopping the box.

## Cost

Claude API usage is the only variable cost: roughly $0.10–0.40 per bill, about $45 for
a full first run over the current Wahlperiode (~340 bills). After that only new or changed
bills are analyzed — a handful per sitting week, well under $5/month. Hosting is one small
EC2 instance, ~$13/month.
